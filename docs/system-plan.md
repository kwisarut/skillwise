## 0. สรุปใน 1 หน้า

**ตัดสินแล้ววันนี้ (2 พ.ย. 2569)**

1. คนเขียนระบบ: ทีมโปรแกรมเมอร์ร่วมกับเจ้าของผลิตภัณฑ์ที่ใช้ AI ช่วยเขียน → สเปกต้องละเอียดพอให้ทั้งคนและ AI ทำงานแยกชิ้นได้ โดยไม่ตีความต่างกัน
2. เทคโนโลยี: **TypeScript ทั้งระบบ · Next.js (หน้าบ้าน) + NestJS (หลังบ้าน) ใน monorepo** ทบทวนและยืนยันเมื่อ 2 พ.ย. 2569 (Context ข้อ 60.5, 60.13.6)
3. Phase 1 ยังไม่กำหนดวันเปิด แต่ **ต้องเสร็จเร็วที่สุด** → แผนในส่วนที่ 11 แบ่งงานเป็นชิ้นเล็กที่ปล่อยได้ทีละชิ้น
4. **เกมห้องนี้ต้องรอด ยังไม่อยู่ในงานสร้างรอบนี้** (แนวคิดอาจเปลี่ยน) ระบบสิทธิ์ออกแบบให้เพิ่มสิทธิ์เกมภายหลังได้ และมอบย้อนหลังให้ผู้ที่เคยกดรหัสในกล่องได้ โดยไม่ต้องสัญญาเรื่องเกมกับลูกค้าตอนนี้
5. **สองส่วนที่สำคัญที่สุด และต้องทำให้ถูกตั้งแต่แรก**: (ก) ระบบสิทธิ์และเครดิต (ข) ระบบซื้อขายและรับเงิน

**หลักใหญ่ 5 ข้อที่ทุกโค้ดต้องเคารพ**

1. **ไม่มีราคาหรือกติกาสิทธิ์เขียนตายในโค้ด** ทุกหน้าจอถามคำถามเดียว "บัญชีนี้มีสิทธิ์ X ไหม / เหลือเครดิต Y เท่าไร" คำตอบมาจากข้อมูลที่ทีมงานตั้งในหลังบ้าน
2. **เงินและสิทธิ์ ห้ามแก้ทับ ห้ามลบ** ทุกการเปลี่ยนเป็นรายการใหม่ (มีคนทำ เวลา เหตุผล) ย้อนดูได้เสมอว่ายอดหรือสิทธิ์มาจากไหน
3. **ยืนยันการจ่ายเงินจากฝั่งผู้ให้บริการรับเงินเท่านั้น** ไม่เชื่อหน้าเว็บฝั่งผู้ใช้ และต้องรับข้อความยืนยันซ้ำได้โดยไม่เปิดสิทธิ์ซ้ำ
4. **โครงข้อมูลรองรับทั้งระบบตั้งแต่ Phase 1** (คน องค์กร สิทธิ์ เครดิต คำสั่งซื้อ เอกสารการเงิน) ส่วนหน้าจอค่อยเพิ่ม
5. **แยกจาก Sila5School โดยสิ้นเชิง** ไม่ใช้ฐานข้อมูล บัญชี หรือข้อมูลครูของ Sila5 ร่วมกัน (ยกได้เฉพาะรายชื่อสถานศึกษาที่เป็นข้อมูลสาธารณะ)

## 4. โครงระบบ

### 4.1 ภาพรวม

โค้ดทั้งหมดอยู่ใน repo เดียว (monorepo: pnpm + Turborepo) แยกเป็นหน้าบ้านกับหลังบ้านตาม Context ข้อ 60.5 ผู้ใช้เห็นเป็นเว็บเดียว เพราะหน้าบ้านกับ API อยู่โดเมนเดียวกันผ่าน reverse proxy

```
skillwise.xxx           หน้าบ้าน (ใครก็เข้าได้) + ร้านค้า + ชำระเงิน      ← apps/web
skillwise.xxx/app       แอปครู (ต้องเข้าสู่ระบบ) — Phase 2 เป็นต้นไป      ← apps/web
skillwise.xxx/school    พื้นที่โรงเรียน — Phase 3                         ← apps/web
skillwise.xxx/admin     หลังบ้าน (ทีมงาน + ยืนยัน 2 ขั้น)                  ← apps/web (ข้อมูลผ่าน API)
skillwise.xxx/api/...   API ของทุกช่องทาง + จุดรับข้อความจากระบบรับเงินและ LINE  ← apps/api
ตัวทำงานเบื้องหลัง       ส่งข้อความ, ทำ PDF, ตรวจยอดเงิน, ตัดบัตรรายเดือน, งาน AI  ← apps/api (worker)
```

- `apps/web` ไม่เชื่อมฐานข้อมูลและไม่มี business logic · ทุกอย่างผ่าน API
- `apps/api` ตรวจสิทธิ์ที่ guard ทุก endpoint และค่าเริ่มต้นคือปฏิเสธ

### 5.2 รายการสิทธิ์ตั้งต้น (catalog)

เก็บเป็นตาราง ทีมงานเพิ่มได้ แต่ **รหัสสิทธิ์ต้องตรงกับที่โค้ดเช็ก** จึงให้โปรแกรมเมอร์เป็นคนเพิ่มรหัสใหม่ ส่วนทีมงานจับใส่แพ็กเกจเอง

| รหัสสิทธิ์ | ความหมาย | ใช้เมื่อ |
|---|---|---|

### 5.4 วิธีที่ระบบตอบว่า "มีสิทธิ์ไหม"

มีฟังก์ชันกลางเพียงชุดเดียว ทุกหน้าจอ ทุก API และทุกงานเบื้องหลังเรียกผ่านตัวนี้ ห้ามเขียนเงื่อนไขเองในหน้าจอ

```ts
can(account, 'cards.teacher_edition')                 // true/false
limit(account, 'classroom')                           // ค่าพื้นฐานมากสุด + โบนัสรวม
bestDiscount(account, seatPool)                       // ส่วนลดดีที่สุดที่กองที่นั่งนี้รับ (ไม่ซ้อน)
creditBalance(account, 'coach_session')               // ยอดคงเหลือที่ยังไม่หมดอายุ
useCredit(account, 'coach_session', amount, ref)      // หักแบบปลอดภัย (amount > 1 ได้ เช่น ร่างทั้งใบ)
```

วิธีคิด

1. รวมการได้สิทธิ์ที่ **ใช้งานอยู่ ณ ตอนนี้** ของบัญชีนั้น + ของโรงเรียนที่บัญชีนั้นได้ที่นั่ง
2. สิทธิ์แบบใช้ได้/ไม่ได้: มีอย่างน้อย 1 รายการ = ได้
3. สิทธิ์แบบตัวเลข: ชนิด "ใช้ค่ามากสุด" เลือกค่ามากสุด · ชนิด "บวกเพิ่ม" รวมกัน · ห้องเรียน = มากสุดของ `classroom.limit` + ผลรวม `classroom.bonus`
4. ส่วนลด: กองที่นั่งแต่ละกองระบุว่ารับส่วนลดแบบไหนบ้าง (ส่วนลด Pro / คูปองผู้ซื้อการ์ด) · ใช้แบบที่ดีที่สุดแบบเดียว ไม่ซ้อน · ถ้าเลือกใช้คูปอง ระบบหักคูปองเมื่อชำระเงินสำเร็จ และคืนคูปองถ้าคำสั่งซื้อถูกยกเลิก/คืนเงิน
5. เครดิต: ยอดคงเหลือ = รวมรายการในสมุดเครดิตที่ยังไม่หมดอายุ · หักจากก้อนที่ **หมดอายุก่อนก่อน** · ยอดติดลบไม่ได้
6. **หักเครดิตในธุรกรรมเดียวกับการเริ่มงาน** และล็อกแถวไว้ เพื่อไม่ให้กดพร้อมกัน 2 ครั้งแล้วใช้เกินยอด · ถ้างาน AI ผิดพลาด ระบบคืนเครดิตอัตโนมัติเป็นรายการบวก

### 5.5 การได้สิทธิ์ (grant) — ข้อมูลที่ต้องเก็บ

`ผู้ได้ (บัญชี/องค์กร)` · `แพ็กเกจและเวอร์ชัน` · `แหล่งที่มา` (สมัครสมาชิก / รหัสในกล่อง / คำสั่งซื้อ / ทีมงานให้เอง / ย้ายจากบัญชีอื่น) + เลขอ้างอิง · `วันเริ่ม` · `วันหมด` · `สถานะ` (รอเริ่ม / ใช้งานอยู่ / หมดอายุ / ยกเลิก) · `ผู้ทำ + เหตุผล` (ถ้าทีมงานทำ)

- **1 การซื้อหรือ 1 การกดรหัส สร้างการได้สิทธิ์ได้หลายรายการ** เมื่อส่วนต่าง ๆ มีวันเริ่ม วันหมด หรือผู้รับต่างกัน เช่น รหัสในกล่อง = (ก) วิดีโอ + คู่มือ ได้ทันทีไม่หมดอายุ (ข) Pro 3 เดือน รอเริ่ม (ค) คูปอง 1 ใบในสมุดเครดิต · ทุกรายการจากแหล่งเดียวกันผูกด้วยเลขอ้างอิงชุดเดียว เพื่อยกเลิกพร้อมกันได้
- สถานะ "รอเริ่ม" **ไม่ใส่วันเริ่ม** จนกว่าเงื่อนไขเริ่มจะเกิด (เช่น วันเปิด Pro) แล้วงานเบื้องหลังคำนวณวันเริ่ม/วันหมดตอนนั้น
- สถานะ "ผ่อนผัน" ใช้กับ Pro รายเดือนที่ตัดบัตรไม่ผ่าน (กติกา C) มีวันหมด 7 วัน
- เพิ่มสิทธิ์ใหม่ย้อนหลัง (เช่น เกม เมื่อพร้อม): ทีมงานสั่งมอบสิทธิ์ให้ทุกบัญชีที่เคยกดรหัสชุดที่เลือก ระบบสร้างการได้สิทธิ์ใหม่พร้อมบันทึกเหตุผล
- เปลี่ยนแปลงทุกอย่าง = บันทึกใหม่ ไม่แก้ทับ (ยกเลิก = ใส่วันยกเลิกและเหตุผล)
- ทีมงานให้สิทธิ์เอง (เช่น ชดเชยลูกค้า) ต้องกรอกเหตุผลทุกครั้ง และจำกัดเฉพาะบทบาทที่อนุญาต
- งานประจำวันเปลี่ยนสถานะ "รอเริ่ม → ใช้งานอยู่ → หมดอายุ" และส่งข้อความเตือนก่อนหมด
- **วันเวลาเก็บเป็นเวลาสากล (UTC) แสดงผลเป็นเวลาไทย** วันหมดอายุนับถึงสิ้นวันตามเวลาไทย

### 5.6 สมาชิก Pro รายเดือน (ต่ออายุอัตโนมัติ)

- แต่ละรอบที่ตัดเงินสำเร็จ = การได้สิทธิ์ใหม่ 1 รอบ + เครดิตรายเดือนใหม่ (หมดอายุสิ้นรอบ)
- **รอบเดือนของเครดิตนับจากวันเริ่ม Pro ทุกแบบ** (รายปี รายเดือน และจากรหัส) ไม่ใช่เดือนตามปฏิทิน เช่น เริ่ม 5 ธ.ค. → เครดิตรอบ 5 ธ.ค.–4 ม.ค. · Pro รายปีและ Pro จากรหัส งานเบื้องหลังเติมเครดิตทุกวันครบรอบ · รอบสุดท้ายหมดไม่เกินวันหมด Pro
- ยกเลิก = หยุดต่ออายุ ใช้ได้ถึงสิ้นรอบ (ไม่คืนเงินบางส่วน)
- เปลี่ยนจากรายเดือนเป็นรายปี: ยกเลิกรายเดือน แล้วรายปีเริ่มต่อท้ายรอบปัจจุบัน
- ตัดไม่ผ่าน: ตามกติกา C ในส่วนที่ 2

### 5.7 ชุดทดสอบที่ต้องมีก่อนเปิดจริง (ส่วนสิทธิ์)

ทุกกรณีต่อไปนี้ต้องเป็นการทดสอบอัตโนมัติที่ผ่านทุกครั้งก่อนปล่อยโค้ด

1. บัญชีใหม่ได้สมาชิกฟรีพร้อมเครดิต 2+2
2. กดรหัสในกล่องก่อนวันเปิด Pro → Pro อยู่สถานะรอเริ่ม (ไม่มีวันเริ่ม) · วิดีโอ คู่มือ คูปอง ใช้ได้ทันที
3. เลื่อนวันเปิด Pro ในหลังบ้าน → Pro ที่รอเริ่มยังถูกต้อง · เมื่อเปิด Pro ทุกบัญชีได้ 3 เดือนนับจากวันเปิด
4. กดรหัสหลังเปิด Pro → Pro 3 เดือนนับจากวันกด
5. มี Pro รายปีอยู่ แล้วกดรหัส → ต่อท้าย
6. มี Pro รายเดือน แล้วกดรหัส → ไม่ถูกตัดเงินซ้อนกับช่วง Pro ฟรี (กติกา A2)
7. กดรหัสกล่องที่ 2 ในบัญชีเดียวกัน → ระบบไม่ยอมใช้ รหัสยังใช้ได้กับบัญชีอื่น (กติกา B)
8. Pro รายเดือนไม่มี `seat.free_zoom` · Pro รายปีมี
9. ส่วนลดไม่ซ้อน: มี Pro + คูปองผู้ซื้อการ์ด = 30% ไม่ใช่ 60% · คูปองใช้ได้ 1 ครั้ง · ยกเลิกคำสั่งซื้อแล้วคูปองกลับมา
10. ผู้ซื้อการ์ดที่ชำระแล้วแต่ยังไม่ได้ของ ใช้คูปองได้ · กดรหัสภายหลังไม่ได้คูปองซ้ำ
11. ห้องเรียน: สมาชิกฟรี 1 + โบนัสสมุด 1 = 2 ห้อง
12. หักเครดิตพร้อมกัน 2 คำขอ เหลือ 1 → สำเร็จ 1 ไม่สำเร็จ 1 · หักครั้งละ 2 (ร่างทั้งใบ) เมื่อเหลือ 1 → ไม่สำเร็จ
13. งาน AI ผิดพลาด → เครดิตคืน
14. เครดิตรายเดือนหมดตามรอบวันเริ่ม Pro · ชุดเติมยังอยู่ · ใช้ก้อนที่หมดก่อนก่อน
15. Pro รายเดือนตัดบัตรไม่ผ่าน → ยังใช้ได้ 7 วัน (ผ่อนผัน) → แล้วกลับเป็นฟรี
16. Pro หมด → ห้องที่ 2 ขึ้นไปอ่านได้อย่างเดียว ข้อมูลไม่หาย
17. ทีมงานย้ายรหัสไปบัญชีอื่น → บัญชีเดิมหมดทุกสิทธิ์จากรหัสนั้น บัญชีใหม่ได้ มีบันทึกผู้ทำ

- สต็อกและที่นั่ง: เก็บเป็นรายการรับเข้า/ตัดออก · **กันของไว้ตั้งแต่สร้างคำสั่งซื้อ** (มีวันหมดอายุตามเวลาจ่ายเงินของคำสั่งซื้อนั้น) ตัดจริงเมื่อชำระสำเร็จ ปล่อยคืนเมื่อหมดเวลาหรือยกเลิก · ทำในธุรกรรมที่ล็อกยอดคงเหลือ เพื่อไม่ให้ 2 คนได้ชิ้นสุดท้ายพร้อมกัน · คำสั่งซื้อแนบสลิปกันของไว้จนทีมงานตรวจเสร็จ
- ของหมด = ปิดปุ่มซื้อ เปิดปุ่ม "แจ้งฉันเมื่อวางขาย" + รับใบเสนอราคาแทน · สมุดบันทึกความสุขขายให้โรงเรียนเท่านั้น

### 6.2 สถานะคำสั่งซื้อ (O5 + สถานะที่แผนนี้เพิ่ม)

สถานะจาก O5: รอชำระ → รอตรวจเงิน → รอแพ็กส่ง → ส่งแล้ว → เปิดใช้รหัสแล้ว · ยกเลิกได้ถึงก่อนแพ็ก
**สถานะที่เพิ่ม** (จำเป็นต่อเงินจริง): ชำระไม่ครบ · หมดเวลาชำระ · เสร็จสิ้น (สินค้าดิจิทัล/ที่นั่ง) · คืนเงินแล้ว / คืนเงินบางส่วน

```
รอชำระ ──(จ่ายผ่านระบบรับเงิน: ยืนยันอัตโนมัติ)───────────────────────┐
   │                                                                ▼
   └─(โอนแนบสลิป)→ รอตรวจเงิน ─(ทีมงานยืนยัน)→ [ชำระแล้ว] → รอแพ็กส่ง → ส่งแล้ว → เปิดใช้รหัสแล้ว
                      └─(ยอดขาด)→ ชำระไม่ครบ ─(โอนส่วนที่ขาด)→ รอตรวจเงิน
                                       (ที่นั่ง / สมาชิก / ชุดเติม: ชำระแล้ว → เสร็จสิ้น)
ทางแยก: ยกเลิก (ได้ถึงก่อนแพ็ก) · หมดเวลาชำระ · คืนเงินแล้ว / คืนเงินบางส่วน
```

- เวลาจ่ายเงิน: QR พร้อมเพย์อายุ 15 นาที (F9) สร้างใหม่ได้ · คำสั่งซื้อปกติหมดเวลาใน [24 ชม.] · **คำสั่งซื้อจากใบเสนอราคาหมดเวลาตามวันยืนราคาของใบนั้น** (โรงเรียนจ่ายช้าได้)
- เปลี่ยนสถานะได้ตามลูกศรเท่านั้น (เขียนเป็นตารางกติกาในโค้ด) ทุกการเปลี่ยนบันทึกผู้ทำและเวลา
- ตอนแพ็กของ ทีมงานสแกน/บันทึกรหัสในกล่องที่ใส่ไปกับคำสั่งซื้อ · "เปิดใช้รหัสแล้ว" = มีรหัสในคำสั่งซื้อถูกกดอย่างน้อย 1 รหัส และเก็บจำนวนที่กดแล้ว / ทั้งหมด ไว้ด้วย (ตัวชี้วัด "ผู้ซื้อที่เปิดใช้จริง" นับจากตรงนี้)

### 6.3 การรับเงิน

แยก **การชำระ (payment)** ออกจาก **คำสั่งซื้อ** · 1 คำสั่งซื้อมีความพยายามจ่ายได้หลายครั้ง (เช่น QR หมดอายุแล้วสร้างใหม่)

| วิธี | ยืนยันอย่างไร | ใช้เมื่อ |
|---|---|---|
| พร้อมเพย์ QR ผ่านระบบรับเงิน | ระบบรับเงินแจ้งกลับ (webhook) → **เราถามยืนยันกลับไปที่ระบบรับเงินอีกครั้ง** → ยอดตรง → ชำระแล้ว | หลักสำหรับครู |
| บัตรเครดิต/เดบิต | เหมือนกัน (มีขั้นยืนยันตัวตนบัตรของธนาคาร) | ครู, Pro รายเดือน |
| โอนเข้าบัญชีบริษัท + แนบสลิป | ทีมงานดูสลิปแล้วกดยืนยัน (จะใช้บริการอ่านสลิปช่วยก็ได้ แต่คนยังกดยืนยัน) | ทางสำรองตอนระบบรับเงินยังไม่อนุมัติ, โรงเรียนจ่ายตามใบเสนอราคา |

กติกาบังคับ (ห้ามข้าม)

1. **รับข้อความแจ้งจากระบบรับเงินซ้ำได้โดยผลไม่ซ้ำ** (เก็บรหัสเหตุการณ์ที่เคยรับแล้ว) — ระบบรับเงินส่งซ้ำเป็นเรื่องปกติ
2. **ตรวจลายเซ็นของข้อความแจ้ง** และถามยืนยันสถานะจากระบบรับเงินก่อนเปลี่ยนเป็น "ชำระแล้ว"
3. **ยอดเงินและสกุลเงินต้องตรงกับ "ยอดที่ต้องได้รับ"** (ยอดคำสั่งซื้อ หักภาษี ณ ที่จ่ายที่บันทึกไว้ ถ้ามี) · ขาด = ชำระไม่ครบ แจ้งลูกค้า · เกิน = แจ้งทีมงานคืนส่วนเกิน · ไม่ตรงห้ามเปิดสิทธิ์
4. การเปิดสิทธิ์ / ตัดสต็อก / ออกใบเสร็จ หลังจ่ายเงิน ทำในงานเบื้องหลังที่ลองซ้ำได้ และไม่ทำซ้ำถ้าเคยทำแล้ว
5. **งานตรวจยอดทุกวัน**: เทียบรายการจากระบบรับเงินกับคำสั่งซื้อในระบบ ไม่ตรงกันขึ้นในกล่องงานฝ่ายบัญชี
6. กุญแจลับของระบบรับเงินอยู่ในที่เก็บความลับของโฮสต์เท่านั้น ห้ามอยู่ในโค้ด

### 6.4 การคืนเงิน

- บันทึกการคืนเงินเป็นรายการ (เต็ม/บางส่วน, เหตุผล, ผู้อนุมัติ)
- คืนเงินแล้ว ระบบตามยกเลิกสิ่งที่เกิดจากคำสั่งซื้อนั้น:
  - สมาชิก/ชุดเติม: ยกเลิกการได้สิทธิ์ และเครดิตที่ **ยังไม่ได้ใช้** (เครดิตที่ใช้ไปแล้วไม่ทวงคืน ยอดไม่ติดลบ บันทึกจำนวนที่ใช้ไว้ประกอบการคิดเงินคืน)
  - การ์ดที่ส่งแล้ว: รหัสในกล่องของคำสั่งซื้อนั้น ที่ยังไม่กด → ยกเลิกรหัส · ที่กดแล้ว → ยกเลิกสิทธิ์ที่ได้จากรหัสนั้น (ทีมงานยืนยันก่อน)
  - คูปองที่ได้จากคำสั่งซื้อนั้น: ยกเลิก ถ้ายังไม่ใช้
- **ข้อควรรู้**: เอกสารของ Opn (Omise) ระบุว่าการจ่ายด้วยพร้อมเพย์ยกเลิกหรือคืนเงินผ่านระบบไม่ได้ ถ้าเลือกเจ้านี้ ต้องคืนเงินพร้อมเพย์ด้วยการโอนเองแล้วบันทึกในระบบ · เจ้าอื่นต้องตรวจเงื่อนไขเดียวกันก่อนเลือก

### 6.7 รหัสในกล่อง

- รูปแบบ SKW-XXXX-XXXX ใช้ตัวอักษรที่ไม่สับสน (ตัด 0/O, 1/I/L) · เก็บรหัสแบบเข้ารหัสทางเดียวสำหรับค้นหา + 4 ตัวท้ายไว้ให้ทีมงานดู
- ส่งออก PDF สติกเกอร์ / CSV ให้โรงพิมพ์ได้ **ครั้งเดียวต่อชุด** (ส่งซ้ำต้องมีสิทธิ์พิเศษและบันทึก)
- สถานะ: สร้างแล้ว → ส่งโรงพิมพ์ → อยู่ในกล่อง → เปิดใช้แล้ว · ยกเลิก (ทั้งรหัสหรือทั้งชุด)
- **กันการเดารหัส**: จำกัดจำนวนครั้งที่ผิดต่อบัญชีและต่อเครื่อง (เช่น ผิด 5 ครั้งรอ 15 นาที)
- รหัสไม่ผูกกับช่องทางขาย ขายผ่าน Shopee หรือตัวแทนได้ รหัสพาคนกลับมาที่แพลตฟอร์มเอง
- ทีมงานย้ายสิทธิ์ไปบัญชีอื่นได้ (ครูกดผิดบัญชี) ต้องกรอกเหตุผล

### 6.9 ชุดทดสอบที่ต้องมีก่อนเปิดจริง (ส่วนซื้อขาย)

1. จ่ายพร้อมเพย์สำเร็จ → ชำระแล้ว → เข้าคิวแพ็ก → ใบเสร็จส่งทาง LINE + อีเมล

5. QR หมดอายุ → สร้างใหม่ได้ คำสั่งซื้อเดิมไม่ซ้ำ

8. ผู้ซื้อการ์ดสมัครเวิร์กช็อป onZoom ครั้งแรก → 630 บาท · ครั้งที่ 2 → 900 · คนทั่วไป 900 · onSite ไม่รับคูปองนี้

## 7. บัญชี ผู้ใช้ และโรงเรียน

- **1 คน = 1 บัญชี** ผูกได้ทั้ง Google และ LINE (ถ้าอีเมลซ้ำ ให้ถามยืนยันก่อนรวม ไม่รวมเอง)
- เข้าครั้งแรก 3 ขั้น (ตามภาพปลายทาง F8): LINE/Google → บทบาท + ค้นหาโรงเรียน หรือเพิ่มใหม่ + เลือก "ใช้คนเดียว / สร้างทีมโรงเรียน" (ทีมเปิดใช้ Phase 3) + ยอมรับนโยบาย → เพิ่มเพื่อน LINE · ที่อยู่จัดส่งถามตอนชำระเงิน
- บทบาทเก็บหลายค่าต่อคนได้ (ครู + ผู้ประสานงาน) สลับมุมมองในบัญชีเดียว
- **ฐานข้อมูลสถานศึกษา**: ตั้งต้นจากรายชื่อสถานศึกษาสาธารณะ · ชื่อที่ผู้ใช้พิมพ์เพิ่มอยู่สถานะ "รอตรวจ" หลังบ้านเสนอชื่อคล้ายให้รวม (A4)
- **องค์กร (โรงเรียน)**: สร้างโครงไว้ตั้งแต่ Phase 1 (ผูกครูกับโรงเรียน, ออกใบเสนอราคาในนามโรงเรียน) · ทีมครู คำเชิญ ที่นั่ง เปิดใช้ Phase 3
- **ทีมงาน**: เข้าด้วย Google ของบริษัท + ยืนยัน 2 ขั้น · บทบาท: ฝ่ายแพ็กของ, ฝ่ายบัญชี, ฝ่ายอบรม, ฝ่ายเนื้อหา, ผู้ดูแลระบบ · แต่ละบทบาทเห็นเฉพาะเมนูของตัวเอง
- ความยินยอม: เก็บว่าใครยอมรับนโยบายเวอร์ชันไหนเมื่อไร · ยินยอมรับข่าวสารแยกจากการแจ้งเรื่องคำสั่งซื้อ

## 10. ความปลอดภัย ข้อมูลส่วนบุคคล และการดูแลระบบ

- ทุกหน้าในแอปและหลังบ้านเช็กสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ ไม่พึ่งการซ่อนปุ่ม
- ทีมงานยืนยัน 2 ขั้น · แยกบทบาท · เบอร์/ที่อยู่ปิดบางส่วน เปิดดูแล้วบันทึก
- บันทึกการเปลี่ยนแปลง (audit) สำหรับเงิน สิทธิ์ รหัส เอกสาร และข้อมูลส่วนบุคคล — ห้ามลบ
- สำรองฐานข้อมูลอัตโนมัติรายวัน + ย้อนเวลาได้ · ทดลองกู้คืนจริง 1 ครั้งก่อนเปิดรับเงิน
- ไฟล์ส่วนตัว (สลิป เอกสาร คู่มือมีชื่อ) เปิดด้วยลิงก์หมดอายุเท่านั้น
- คู่มือครูใส่ชื่อและอีเมลผู้ซื้อทุกหน้า · วิดีโอที่ต้องมีสิทธิ์เล่นได้เฉพาะในเว็บเรา (Phase 1 ถ้าเร่ง ใช้ YouTube แบบไม่แสดงในรายการชั่วคราวได้ แต่ถือว่าส่งต่อได้)
- นโยบายความเป็นส่วนตัวต้องบอกว่าเซิร์ฟเวอร์อาจอยู่นอกประเทศ (สิงคโปร์) · เก็บข้อมูลเท่าที่จำเป็นต่อการส่งของและออกเอกสาร
- จำกัดจำนวนคำขอ: เข้าสู่ระบบ, กดรหัส, ขอใบเสนอราคา, ส่งสลิป
- ตรวจไฟล์ที่อัปโหลด (ชนิดและขนาด) · สลิปรับเฉพาะรูปภาพ/PDF

## 12. วิธีทำงานร่วมกัน คน + AI

1. **สเปกก่อนโค้ด**: ทุกงานเริ่มจากไฟล์สเปกสั้น ๆ ใน `docs/` (คัดจากเอกสารนี้) ระบุ: ทำอะไร, ข้อมูลที่ใช้, สถานะ, กรณีพิเศษ, ทดสอบอะไร · สั่ง AI จากไฟล์สเปก ไม่สั่งปากเปล่า
2. **CLAUDE.md และ AGENTS.md** (มีอยู่แล้วใน repo ให้เพิ่มกติกาลงไป) เขียนกติกาให้ AI: โครงโฟลเดอร์ในส่วนที่ 4.3, ห้ามเขียนตรรกะเงิน/สิทธิ์ในหน้าจอ, เงินเป็นสตางค์, ห้ามแก้/ลบรายการเงินและสิทธิ์, ต้องเขียนทดสอบคู่ทุกการแก้ใน entitlements/commerce/payments/documents, คำศัพท์ตามส่วนที่ 5.1, ข้อความไทยบนหน้าจอเป็นภาษาง่าย ไม่ใช้คำว่า "พัง"
3. **ทุกการแก้โค้ดผ่านการตรวจโดยคน** (pull request) · โค้ดเงินและสิทธิ์ต้องมีผู้ตรวจที่ไม่ได้เป็นคนเขียน
4. **ระบบตรวจอัตโนมัติ** รันทุกครั้งที่ส่งโค้ด: ตรวจชนิดข้อมูล, ตรวจรูปแบบ, ชุดทดสอบ · ไม่ผ่าน = ปล่อยไม่ได้
5. **การเปลี่ยนโครงฐานข้อมูล** ทำผ่านไฟล์ migration เท่านั้น ห้ามแก้ฐานข้อมูลจริงด้วยมือ
6. **ข้อมูลตัวอย่าง** (seed) สำหรับ staging: แพ็กเกจตามส่วนที่ 5.3, สินค้า, ครูตัวอย่างทุกบทบาท, รหัสในกล่องทดสอบ
7. **บันทึกการตัดสินใจ:** เรื่องใหม่ที่ตัดสินระหว่างสร้าง ให้แก้ Context (`docs/SkillwisE-Canonical-Context-updated.md`) ทันที บันทึกลงข้อ 60 พร้อมวันที่และป้าย และถ้ากระทบเอกสารนี้ก็แก้เอกสารนี้ด้วย
8. **นิยาม "เสร็จ"**: ทำตามสเปก + ทดสอบผ่าน + ขึ้น staging + เจ้าของผลิตภัณฑ์หรือผู้รับผิดชอบกดลองแล้ว

## 13. ความเสี่ยงหลัก

| ความเสี่ยง | ผลกระทบ | ทางป้องกัน |
|---|---|---|
| ระบบรับเงินอนุมัติช้า | ขายผ่านบัตร/พร้อมเพย์อัตโนมัติไม่ได้ | ยื่นวันนี้ · เปิดขายด้วยโอน + สลิปก่อน |
| ตัดบัตรรายเดือนไม่ได้กับบัตรไทยที่ต้องยืนยันตัวตน | Pro รายเดือนใช้ไม่ได้ | ถามผู้ให้บริการก่อนเลือก · Pro รายปีไม่ติดปัญหานี้ |
| บริษัทยังไม่จด VAT / ข้อมูลภาษีไม่ครบ | ออกใบกำกับภาษีให้โรงเรียนไม่ได้ ขายโรงเรียนยาก | ถามผู้ทำบัญชีสัปดาห์นี้ |
| ทีมใหม่ + AI เขียนเร็วแต่ตรรกะเงินผิดพลาด | เงินหรือสิทธิ์ผิด ลูกค้าเสียความเชื่อใจ | ชุดทดสอบส่วนที่ 5.7 และ 6.9 บังคับ + ผู้ตรวจคนที่สอง |
| ราคา/กติกาเปลี่ยนบ่อย | ต้องแก้โค้ดบ่อย | ทุกอย่างมาจากแพ็กเกจในหลังบ้าน + เวอร์ชัน |
| โควตา LINE ไม่พอ | ข้อความแจ้งเตือนส่งไม่ออก หรือค่าใช้จ่ายเกิน | ตรวจแพ็กเกจปัจจุบัน · ใช้อีเมลคู่ · ตั้งเพดาน |
| คู่มือครู PDF ถูกส่งต่อ | เสียรายได้ | ใส่ชื่อทุกหน้า · ของที่มีค่าที่สุดอยู่บนแพลตฟอร์ม (Pro, วิดีโอ, เกม) |
